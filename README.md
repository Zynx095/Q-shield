# Q-SHIELD

**Continuous device trust with post-quantum-signed evidence.** A working prototype built for a hackathon.

> Authentication answers "who are you" once. Q-SHIELD keeps asking "can I still trust you", continuously, using
> post-quantum-signed evidence.

A device that authenticated correctly can still be compromised: its enclosure opened, its configuration changed, its
surroundings breached. Q-SHIELD keeps scoring every device from independent evidence (cryptographic identity, the
physical tamper switch, sensor ranges, configuration integrity, network liveness, and signed camera observations). It
quarantines a device at the gateway when the evidence turns against it, records every decision in a signed evidence
chain, and only lets the device back after a verified, operator-started recovery rebuilds its trust.

## What is real, and what is simulated

| Part | Status |
|---|---|
| Gateway, trust engine, quarantine enforcement, recovery orchestrator, digital twin, evidence chain, operator identities, dashboard | **Real and tested.** FastAPI + SQLite, exercised over HTTP. |
| Vision service | **Real.** OpenCV capture, YOLO11n detection and configurable zones. The camera is also watched as part of the security boundary: covered or blinded, frozen feed, view changed (turned or redirected), degraded (low light or blur), plus image-space proximity heuristics (no distance is measured). Run live on a USB webcam for start-up, warm-up, a normal scene, person detection and proximity. Covering, turning and freezing the camera are tested on synthetic frames only. Detection accuracy has not been measured. |
| Post-quantum cryptography | **Real, on the vision path only.** ML-KEM-768 (FIPS 203) and ML-DSA-65 (FIPS 204) via `pqcrypto`, checked against NIST ACVP vectors. ML-DSA-65 also signs the evidence chain. |
| Device telemetry | **Simulated.** A software agent (`device_agent/`) speaks the real device protocol and registers as `hw: software-agent`. It can also replay recorded readings. The dashboard labels its data **Simulated**. |
| Device authentication | **HMAC-SHA256** with a provisioned secret and a replay counter. **Not post-quantum.** |
| ESP32 firmware | **Skeleton only.** It has never been compiled or flashed (`hardware/esp32/`). The device contract and byte-exact test vectors are published (`docs/hardware/`), so the board needs an adapter, not gateway changes. |
| Attacks in the demo | **Synthetic.** Generated by `attack_simulation/` and sent through the real gateway. The demo's visual violation is a synthetic detection signed with the real vision key, and it is labelled Simulated. |
| Digital twin | Compares expected and **self-reported** state. A match is evidence, **not attestation**. |
| "Self-healing" | **Software remediation and earned trust.** It cannot repair hardware or reflash firmware. |
| Browser camera preview (Camera & vision page) | **Local only.** Not analysed, signed or sent to the gateway. Signed observations come only from the Python vision service. |

## How it works

```
 Device (software agent today)  --HMAC-SHA256 envelope-->  Gateway (FastAPI)
 Vision service (OpenCV+YOLO11n)  --ML-DSA-65 signed, optionally inside an ML-KEM-768 / AES-256-GCM session-->  Gateway
 Operator (dashboard / API)  --named bearer token, roles, optional TLS-->  Gateway

 Gateway: authenticate -> store -> trust engine -> enforcement -> recovery orchestrator
                                 \-> digital twin             \-> evidence chain (SHA-256 linked, ML-DSA-65 signed)
```

- **Trust engine** (`backend/trust/`). It is deterministic and explainable: every score change lists the reasons that
  sum to it.
  - Six factors carry fixed weights: identity 25%, physical 20%, configuration 15%, sensor 15%, visual 15%,
    network 10%.
  - Thresholds: TRUSTED at 80 and above, quarantine below 50, back to TRUSTED only at 85 (hysteresis).
  - Unauthenticated traffic (forged or replayed messages) adds only bounded pressure, capped at 25 points. On its own
    it can never quarantine a device.
  - Caps hold the score down while a condition lasts: confirmed incident 30, tamper 55, repeated replay 65, integrity
    mismatch 65, stale device 79.
  - An incident needs two independent kinds of evidence within 60 s. Examples: an authenticated tamper report plus a
    signed camera observation, or plus a signed report that the camera was covered, frozen or turned away. Camera
    evidence alone never quarantines, and one camera cannot corroborate itself.
  - States: TRUSTED, SUSPICIOUS, QUARANTINED, RECOVERING, VERIFIED, RECOVERED. QUARANTINED is sticky. Recovery states
    fall back to QUARANTINED on any authenticated fault.
- **The camera as part of the security boundary** (`ai/vision/health.py`, `ai/vision/proximity.py`). The vision
  service checks the camera itself, from simple image statistics against a reference view learned at start-up:
  - **obstructed:** covered, facing a blank surface, or blinded by a light;
  - **frozen:** the same frame repeated;
  - **view changed:** turned, tilted or redirected, with the shift measured;
  - **degraded:** low light with the scene still visible, or blur.

  A state is reported only after it has held for 2 s, so a flicker or a passing hand is not. People the detector
  sees are masked out, so someone walking through is not a moved camera. A person very close to the camera, or
  approaching it fast, is reported as an **image-space heuristic** (bounding-box share of the frame); no distance is
  measured. Thresholds are unvalidated defaults.
- **Bounded rejection logging** (`backend/security/rejections.py`). Unauthenticated rejections (forged, replayed,
  unknown identities) are sampled per sender and per 10 s, and the rest are coalesced into one record with the count.
  Old routine rows are pruned only after the trust engine has read them. Authenticated misbehaviour and enforcement
  are always kept. A test shows trust decisions are identical with and without sampling.
- **Quarantine enforcement** (`backend/security/enforcement.py`). In QUARANTINED, RECOVERING and VERIFIED the
  device's normal channel is refused with 403 after authentication, and only the recovery channel stays open.
  Unauthenticated traffic is rejected before enforcement, so it can neither trigger quarantine nor slip past it.
- **Recovery** (`backend/recovery/orchestrator.py`). Each stage is authenticated and recorded:
  1. An operator starts recovery.
  2. The gateway sends a known-good configuration command over the recovery channel, and the device acknowledges it.
  3. Three consecutive clean reports are required, **each judged on its own content**: tamper closed, and every
     expected field reported and matching.
  4. The device reaches VERIFIED, then rebuilds trust from fresh evidence: RECOVERED (normal access back) at 50,
     TRUSTED at 85.

  Deadlines are 15 minutes to verify and 2 hours to rebuild trust, enforced by a background timer. Every failure
  returns the device to QUARANTINED. The known-good state is frozen while a recovery runs.
- **Digital twin** (`backend/twin/`). Operator-set expected firmware, configuration, capabilities and sensor ranges
  against the device's authenticated self-reports, with the time each field was last reported.
- **Evidence chain** (`backend/evidence/chain.py`). Every trust change, enforcement and control action is appended
  as a SHA-256 linked entry signed with ML-DSA-65 by the gateway. Verification recomputes every hash and checks every
  signature, so an edited, reordered or removed entry is found.
- **Operators** (`backend/security/operators.py`). Named operators hold `qso_` tokens, stored as SHA-256 hashes, with
  roles viewer, operator and admin. Every action is attributed in the evidence chain. HTTPS is optional
  (`QSHIELD_TLS_CERT`, `QSHIELD_TLS_KEY`).
- **Dashboard** (`dashboard/`). A light security command center with no build step and no dependencies. It covers the
  overview, devices, incidents, recovery, evidence ledger with a forensic case file, digital twin, cryptography,
  Camera & vision, settings, and a one-screen presentation mode (`#/live`). See `dashboard/README.md`.

## Post-quantum cryptography

| Use | Algorithms | Where |
|---|---|---|
| Signed observations | ML-DSA-65 with FIPS 204 context string `qshield/signed-observation/v1`, over a length-prefixed canonical encoding (never JSON) | `backend/protocol/signed_observation.py` |
| Session for observations | ML-KEM-768 encapsulation, the handshake signed with ML-DSA-65, HKDF-SHA256 key schedule, AES-256-GCM per direction with strict counters, key confirmation | `backend/security/session.py` |
| Evidence chain | ML-DSA-65 over each entry's SHA-256 hash, context `qshield/evidence/v1` | `backend/evidence/chain.py` |

**Replay and freshness:**
- A signed observation is rejected if its signature fails, if it is stale or future-dated (5 minutes skew), if its
  signer is unknown, retired or unauthorised for that device, or if it repeats an observation id.
- A handshake nonce can be used once.
- Session messages must arrive in strictly increasing order.

Every rejection is recorded and counts only as bounded pressure. A flood is sampled and coalesced, with counts kept.
The vision client opens a new session only when the gateway says the old one expired. It backs off on failure and
is limited to 20 handshakes an hour, so persistent rejections cannot exhaust the gateway's session table.

The session protocol is a composition of standard primitives with no external review. It is not TLS. Details,
conformance results and benchmarks are in `pqc/README.md`.

## Run the demo

```
pip install -r backend/requirements.txt              # includes OpenCV and YOLO11n (ultralytics, AGPL-3.0) for the webcam step
python scripts/demo_full.py --webcam --pace 2 --hold
```

The demo starts a real gateway on `127.0.0.1:8765` with scratch keys and a scratch database, then runs the full
story over HTTP:
1. authenticated join and telemetry, with a digital-twin match
2. real webcam frames through YOLO11n, signed observations sent inside an ML-KEM-768 session
3. a forged observation (rejected), then a replay (rejected)
4. a tamper report, correlated with signed visual evidence, triggers quarantine and enforcement
5. evidence-chain verification
6. operator recovery, then health checks, then VERIFIED, RECOVERED and TRUSTED

Open the printed `http://127.0.0.1:8765/dashboard/#token=…` link and choose **Presentation mode**.

- **Camera.** `config/vision.json` sets the camera index (`camera.source`: usually `0` for the built-in camera and
  `1` for the first USB camera). `python -m ai.vision probe --config config/vision.json` tests it, and
  `--vision-config <file>` uses another file.
- **No camera.** The webcam step says so and the rest of the demo runs. Leave out `--webcam` to skip it.
- **Who is in front of the camera matters.** A person in the restricted zone (the right half of the frame by
  default) is a **real** rule violation and lowers trust during step 2. A person whose box covers more than 35% of
  the frame is also reported once as a proximity heuristic, which is a small penalty. Keep that half clear and stand
  back for the scripted story.
- **TIME-LAPSE.** The trust ramp needs about 40 minutes of clean evidence at the documented parameters. The demo
  advances the gateway clock and says so. No parameter is changed.

Step-by-step presenter notes are in `docs/hackathon/demo-plan.md`.

### Your own gateway

```
python scripts/pqc_provision.py init-gateway                 # gateway ML-KEM key (see pqc/README.md)
python scripts/pqc_provision.py enroll-signer ...            # the vision service's ML-DSA identity
python -m backend.main                                       # gateway on :8000, dashboard at /dashboard/
python scripts/operators.py create alice "Alice" operator    # named operator token (printed once)
python scripts/enroll_device.py DEVICE-001                   # enrol a device (HMAC secret)
python -m device_agent --device-id DEVICE-001                # simulated device
python -m ai.vision run --gateway http://127.0.0.1:8000 --signer-id vision-1 --secure   # signed vision service
```

## Limitations

- All device data is simulated, the ESP32 has never been compiled or flashed, and no physical tamper test has been
  done.
- The camera checks and proximity heuristics use simple image statistics with unvalidated thresholds. Covering,
  turning, freezing and unplugging the real camera have not been staged. The reference view is learned when the
  vision service starts, and a change small or slow enough to stay under the thresholds is not detected.
- The device path is HMAC-SHA256 (symmetric, pre-shared key), not post-quantum.
- A device's self-reported state can be faked by a compromised device. There is no secure boot or remote
  attestation, so the twin and the health checks are evidence, not proof.
- Trust parameters are documented design choices (`docs/architecture/trust-engine.md`). They have not been
  calibrated against data.
- The evidence chain is not anchored externally. Whoever holds both the database and the evidence key can rewrite it.
- TLS is optional, and the dev certificate is self-signed. Over the default HTTP, bearer tokens travel in cleartext.
- The system runs as a single process and single gateway (SQLite). Coalesced rejection counts that have not been
  written yet are lost if the gateway stops; the sampled rows are already stored.
