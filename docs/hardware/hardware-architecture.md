# Hardware architecture: from simulated device to ESP32

> **No physical device has been used yet.** Every device result in this repository comes from the software device
> agent, and every ESP32 statement here is a plan. Nothing has been compiled for, flashed to or measured on an
> ESP32. The design goal is that adding the board needs an **adapter**, not a rewrite.

## 1. One protocol, three senders

```
 SIMULATED DEVICE AGENT ─┐                       ┌─ authentication (HMAC-SHA256, counter)
 (device_agent/, today)  │                       ├─ quarantine enforcement
                         ├─► SAME PROTOCOL ────► ├─ digital twin
 REPLAYED RECORDINGS ────┤   (envelope v1,       ├─ trust engine (same signals, same weights)
 (ReplaySensors)         │    docs/hardware/     └─ evidence chain, recovery
                         │    device-protocol.md)
 ESP32 FIRMWARE ─────────┘
 (hardware/esp32/, future)
```

| Layer | Simulated today | With the ESP32 | Change needed |
|---|---|---|---|
| Device identity | A per-device HMAC-SHA256 secret, held by the agent. | The same secret in `secrets.h`, generated by `scripts/enroll_device.py --esp32-secrets`. | None on the gateway. |
| Wire format | `backend/protocol/envelope.py` | `main.cpp` `send()`, checked against the test vectors. | Compile the firmware and check it against the vectors. |
| Tamper switch | `agent.tamper`, driven by the attack simulation. | A reed switch on a GPIO (`QSHIELD_TAMPER_PIN` in `include/board.h`). | Wire it, define the pin, and test the open and closed readings. |
| Environment | `SimulatedSensors` (temperature, vibration). | BME280 (temperature, humidity, pressure) and MPU6050 (vibration). | Driver code in `telemetryPayload()`. Absent sensors stay absent. |
| Network telemetry | Simulated RSSI. | `WiFi.RSSI()`. | Done in the skeleton (not compiled). |
| Firmware / config identity | `fw_version`, `cfg_hash` from the agent. | Firmware constants. | **These are self-reported, not attested.** Secure boot and flash encryption are future work. |
| Camera | USB or built-in webcam through OpenCV. | An ESP32-CAM MJPEG stream, as `camera.source = "http://<ip>:81/stream"`. | A configuration change only. It is labelled `network_camera` (`ai/vision/camera.py describe_source`). It has not been tried with an ESP32-CAM. |
| Recovery channel | `agent.recovery_report()` | Not in the skeleton. | Send `recovery` reports after a 403 `device_quarantined`. |
| Provenance label | `hw = "software-agent"`, and trust signals say "simulated by software-agent". | `hw = "esp32"`, and signals say "self-reported by device". | Automatic, from the `hw` field. |

What does **not** change: the gateway, the trust-engine weights, caps and thresholds, the twin, the evidence chain,
the recovery orchestrator and the dashboard. `tests/security/test_device_vectors.py` shows a gateway accepting a
board's exact bytes (register with `hw: esp32`, telemetry with tamper open) with no code path special to the board.

## 2. What a hardware session must do, in order

1. **Identify the board.** Run `pio device list` and `esptool chip_id`, and record the result in
   `hardware/esp32/README.md`. Set the PlatformIO `board` (today it is the placeholder `esp32dev`).
2. **Compile.** Run `pio run` in `hardware/esp32/firmware`. The skeleton has never been compiled, so expect fixes.
3. **Check the protocol off-line.** Reproduce `tests/vectors/envelope_v1_cases.json` byte for byte on the board,
   for example by printing `send()`'s body with the test key, before any gateway is involved.
4. **Enrol and connect.** Run `python scripts/enroll_device.py <ID> --esp32-secrets
   hardware/esp32/firmware/include/secrets.h ...`, then flash. The gateway log should show register and heartbeat
   accepted, and the device page should show `hw: esp32`.
5. **Wire the reed switch** (`docs/hardware/wiring-plan.md`). Define `QSHIELD_TAMPER_PIN` and confirm: lid closed
   gives `tamper: false`, lid open gives `tamper: true`, and the dashboard shows a physical tamper signal.
6. **Add the BME280 and MPU6050** one at a time. Set realistic ranges in the twin (`PUT
   /api/v1/devices/<id>/twin/expected`), and measure normal readings before choosing them.
7. **Recovery channel.** After a 403 `device_quarantined`, send `recovery` reports. Run the recovery demo with the
   board.
8. **Measure what the trust engine assumes:** heartbeat jitter on Wi-Fi (the 15 s / 45 s staleness timing), the
   delay between opening the lid and the camera seeing it (the 60 s correlation window), and the reed switch's
   false-open rate. Record the results; do not tune parameters to a demo.

## 3. Security notes

- The device secret sits in flash. Without flash encryption, anyone holding the board can read it. Treat a lost
  board as a compromised credential and revoke it (`/api/v1/devices/<id>/revoke`).
- HMAC-SHA256 with a 256-bit key is not threatened by known quantum attacks the way RSA and ECC are. It is still
  **not** a post-quantum signature, and the ESP32 does not run ML-KEM or ML-DSA. Post-quantum protection in this
  system covers the vision service's observations (ML-DSA-65, ML-KEM-768) and the evidence chain.
- The tamper switch, sensor values and firmware identity are **self-reported**. A compromised board can lie. The
  trust engine treats them as evidence, not proof, and corroborates them with the independently signed camera.
